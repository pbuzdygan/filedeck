# Filedeck prototype contract

## Scope and trust boundary

Linux/Docker, a single instance, one or more spaces (directories exposed to users). The directories may be changed outside Filedeck. The configuration of mounts, space directories, the private state directory and the process identity is trusted. The caller of `core.Service` supplies the identity after authentication. In the API, `subject` is exclusively the account ID from a verified server-side session; it never comes from a header or request parameter. The `list`/`read`/`put` commands are a tool for the local operator.

`SetPermissions` is a trusted administrative operation. It is not meant to be exposed directly through the API. The policy is a map space → permissions (List, Read, Create, Modify); the `*` key applies to all spaces, including those added later, and adds up with the entry of a specific space. No entry means denial; an unknown space is rejected like a missing permission. Reading content and listing are independent of creating and modifying. Revoking permissions blocks further operations and upload publication; it does not take away a read handle that is already open. In the server, handles must stay under the control of the operation layer.

## Meaning of a path and a handle

A path is relative, valid UTF-8, up to 4096 bytes, up to 128 segments of at most 255 bytes each. We reject absolute and empty paths, NUL, backslash, `.` and `..` segments, repeated and trailing separators. `.` is an exception for listing the root only. Percent signs are literal name characters; storage URL-decodes nothing. The HTTP adapter decodes the query exactly once (`url.ParseQuery`), accepts exactly one `space` and at most one `path`, and passes the result on without further decoding. Paths are always relative to a space; the same path in another space is a different object.

When resolving a path, `openat2` enforces `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS` and `RESOLVE_NO_XDEV`. For reads, `O_PATH` lets us check the object type before opening the data; `/proc/self/fd` then gives access to the same object. A later replacement of the name with a symlink does not redirect the open handle.

**Object identity boundary:** a handle keeps access to the object even after rename/unlink. If an external process can move an open directory into another trust zone, writes relative to that handle still apply to that directory. The prototype does not continuously check the current path of all open objects. External processes allowed to move directories between zones are not treated as isolated adversaries. This limitation must be taken into account when configuring shares and before supporting elaborate multi-space policies.

Similarly, a hardlink to a confidential file placed by a privileged process in an exported directory is not recognised as "external" by its path. OS permissions and export configuration remain part of the protection. Symlinks, devices and nested mounts are not a way to extend a space: listing does not show them and `RESOLVE_NO_XDEV` does not allow entering them. Every host directory is a separate space (a separate mount).

Sources for the mechanisms: [openat2](https://man7.org/linux/man-pages/man2/openat2.2.html), [renameat2](https://man7.org/linux/man-pages/man2/renameat2.2.html), [golang.org/x/sys/unix](https://pkg.go.dev/golang.org/x/sys/unix). The guarantees described above follow from the operations used and the deployment assumptions, not just from textual validation of names.

## Spaces and the `.filedeck` directory

A space is a directory opened once at startup (`openat2` without symlinks). In the CLI and Docker: the `files` space (`-root`, `/files` in the image) and every subdirectory of `-spaces-dir` (`/spaces/<name>` in the image), with a name matching `^[a-z0-9][a-z0-9._-]{0,63}$`. A symlink or an invalid name in the spaces directory stops the startup (instead of being skipped silently). The state directory must not be inside a space or contain one.

In every writable space Filedeck creates or verifies `.filedeck/` with the subdirectories `staging/` and `trash/`: owned by the process, not writable by group or others (`0700` when created; on CIFS the mode comes from the mount options, so only the absence of `go-w` is required), on the same mount as the space, opened without symlinks. They live inside the space for atomicity: publication and moving to the trash are a single `renameat2` within one filesystem, and spaces may be on different mounts.

`.filedeck` is unreachable for users in two ways: (1) a first path segment equal to `.filedeck` regardless of letter case and trailing dots/spaces (which SMB servers ignore) is rejected; (2) the first segment is compared with `.filedeck` by (device, inode), which catches any alias of the same directory — e.g. 8.3 names or a different Unicode normalisation on the server side. Listing the root also skips it by inode. This applies to all operations: reading, listing, upload, folders, rename (source and target), trash and restore.

A space is **read-only** when the filesystem is mounted `ro` (`ST_RDONLY`) or the process has no write permission on its root directory. In that case `.filedeck` is not created (an existing one stays hidden) and write operations return `ErrReadOnly` (HTTP 403 `read_only`). Uploads in progress in a space that became read-only or disappeared after a restart are abandoned.

Modes of new objects: files `FILEDECK_FILE_MODE` (default `0640`, set with `fchmod` just before publication; staging has `0600`), folders `FILEDECK_DIR_MODE` (default `0750`). The process sets `umask 0`, so the modes are exactly as configured. At least `rw` for the owner of files and `rwx` for directories is required. On mounts that reject `chmod` (`EPERM`/`EOPNOTSUPP`, e.g. CIFS without Unix extensions) the mode stays as imposed by the mount.

## Rename and trash

Both operations require Modify in the space, do not work in read-only spaces and are serialized with session revocation, like a commit.

- **Rename/move** within one space: the source must be a regular file or a directory (symlinks and special files are rejected), both parent directories are opened without symlinks, `renameat2(RENAME_NOREPLACE)` — it never replaces the target. Moving a directory into its own subdirectory or into `.filedeck` is rejected. Moving between spaces is a copy followed by moving the source to the trash (see "Copy and move").
- **Trash**: the record (`trash` in `uploads.db`: ID, space, original path, type, size, time, who deleted it) is written **before** moving the item to `.filedeck/trash/item-<64 hex>`. Restoring moves the item back to the original or a given path, also with `RENAME_NOREPLACE` — a taken name gives 409, a missing target folder 404; the interface then asks for another path.
- **Permanent deletion** only from the trash: in the API administrators only (Modify in the core), automatically after `TrashRetention` (default 30 days, during the periodic `Expire`). Tree removal works relative to directory descriptors, without following symlinks (the symlink is removed, not its target), verifying that the opened directory is the same inode, without crossing devices, with a depth limit of 256 and 1,000,000 entries. Operations on trash records are serialized (`trashMu` always before `policyMu`).
- **Recovery at startup**: a record without an item (a crash before the move, or after a restore/deletion but before the record was removed) is deleted; an item without a record (a crash after the move) is adopted as a record without an original path — it stays visible, can be restored under a given path and expires normally. Records of a space that is temporarily missing are kept.
- The trash can be seen and restored by anyone with Modify in the space — regardless of who deleted the item (the record stores the deleter's ID).

## Preview, editor and copy

**Preview** (`/api/preview`, Read): the type comes only from the extension, from a fixed list (images including SVG, video, audio, PDF), never from the content; `Content-Disposition: inline`, `nosniff`, `Cross-Origin-Resource-Policy: same-origin` and a CSP with `sandbox` — an SVG with a script will not run it either in `<img>` or when opened in a tab. PDF gets `default-src 'none'; frame-ancestors 'self'` without `sandbox` (browsers do not render PDFs in a sandbox). HTML and other types can only be downloaded (415). The page allows `media-src`/`frame-src 'self'`.

**Editor** (`/api/text`): reading requires Read; UTF-8 only without NUL bytes, max 2 MiB; the version = (inode, size, mtime), checked before and after reading. Saving a new file requires Create and never replaces an existing one. Saving an existing file requires Read+Modify and the version: the new content goes to staging (fsync, file mode preserved), the trash record is written, the current file is moved to the trash (`RENAME_NOREPLACE`) and checked against the version — on mismatch it is moved back (409 `changed`) — after which the staging file takes the name (`RENAME_NOREPLACE`). Between the steps the name is briefly absent; a crash at that moment leaves the previous version in the trash. Every save leaves the previous version in the trash (`replaced: true`). At most 4 concurrent saves (buffer of ~12 MiB each), content read before taking the publication lock.

**Copy and move** (`/api/transfers`): the source requires Read (+Modify when moving), the target Create; permissions are checked at the start and again just before publication (under the revocation lock). A move within a space is a rename. The copy goes to `.filedeck/staging/copy-<hex>` of the target space relative to descriptors, without following symlinks and without crossing mounts (symlinks, special files and nested mounts are skipped and counted), files are opened with `O_PATH` and then reopened as the same object; then a single `RENAME_NOREPLACE`. A move between spaces: copy, publication, then the source goes to the trash of the source space. Limits: 256 GiB and 200,000 entries per job, 2 jobs per user, 4 in total. Jobs live in memory; an interrupted copy is removed at startup. A copy is not a snapshot of a source changing meanwhile.

**Search** (`/api/search`, List): names containing the phrase (1–100 characters, no `/` or NUL), below the given folder. The walk is relative to directory descriptors, without following symlinks, without entering other mounts or `.filedeck` (by name and inode), re-checking the inode of each opened directory. Limits: 200,000 scanned entries, 500 results, depth 64, 10 s — when reached, the result is partial (`truncated`) rather than an error. Listings and results include the modification time (`modified`).

**Space reserve**: an upload, an editor save and every copied file are refused (`ENOSPC`, HTTP 507) if they would leave less than `MinFreeBytes` (512 MiB) free on the space's filesystem.

## Public links

**Creation** (`POST /api/links`, session + CSRF): requires Read in the space, and List as well for a folder; the object must exist (a link to a non-existent path is impossible), and the path cannot be the root of the space or `.filedeck`. Validity 1 h – 365 days (mandatory), an optional password of 8–1024 characters. The link stores the space, the path and the **object identity**: device, inode and birth time (`statx` `STATX_BTIME`, when the filesystem reports it). The token is 32 random bytes (base64url) returned only in the creation response as `url` = `FILEDECK_ORIGIN` + `/s/<token>`; the token is decoded strictly (only its canonical spelling is accepted), the database (`links` in `uploads.db`) stores only the SHA-256 of the token, and the password as Argon2id (salted, the same parameters as account passwords, at most 2 computations at once). Limits: 200 links per user, 5000 in total.

**Every use** (the `/s/<token>` page, `/api/public/<token>[/files|/content|/unlock]`, no session): record → expiry → the owner's current permissions in that space → opening the path (`openat2` as everywhere) and comparing the identity. Any mismatch gives a single 404 `link_unavailable` response, without revealing the reason. A link therefore stops working after the object is renamed, moved (including to the trash), deleted or replaced — also when done over SMB or by another application — and after expiry and revocation. Taking Read/List away from the owner or disabling their account **deletes** their links (restoring the permissions does not revive them). Expired records are removed by the periodic cleanup.

**Folder**: listing and downloading only below the handle of the shared folder (`RESOLVE_BENEATH|NO_SYMLINKS|NO_XDEV` relative to its descriptor), rejecting `..`, symlinks, mounts and `.filedeck` by name and by inode (in case someone moves it into the folder). Read-only — nothing can be changed through a link. File: only that file.

**Password**: before unlocking, the API returns only `{"needs_password": true}` (no name or size), and `files`/`content` return 403 `link_locked`. `POST …/unlock` (limit of 10 attempts per minute per address, `Origin` required as everywhere) sets a `__Host-filedeck-link-<id>` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`) with the value `<expiry>.<HMAC-SHA256>`, keyed with a key held only in memory, valid for up to 12 h (never longer than the link). A server restart asks for the password again.

**Download**: always as an attachment (`application/octet-stream`, `nosniff`, CSP `sandbox`), a single `Range`, at most 8 concurrent downloads through links. The public page has the same CSP with Trusted Types as the application, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`. The write deadline of a download (also for signed-in users) moves forward with every written chunk — a large file on a slow connection is not cut off after 60 s, while a client that stopped reading is disconnected.

**List and revocation** (`GET /api/links`, `DELETE /api/links/{id}`): own links with an `available` field; an administrator can fetch all of them (`?all=1`, with the owner's name) and revoke any. The token cannot be read again — create a new link instead of a lost one.

## Upload lifecycle

1. `Begin`: check Create, the path, the size and quotas; reserve the declared size; a random ID, a new `0600` file in the space's `.filedeck/staging` and a durable record (`uploading`, with the space name). If writing the record fails, the staging file is removed.
2. `Patch`: check the owner and Create, lock the specific upload, check the offset and expiry, bounded write and sync. An extra byte is detected without writing it to disk. The new offset goes into the record **only after the data is fsynced**; a 200 response means the chunk survives a crash. A write, fsync or record error truncates the file back to the previous offset. A failed rollback makes the upload impossible to continue.
3. `Commit`: completeness, actual size, current Create in the space, apply the `FILEDECK_FILE_MODE` mode and sync the file. The record moves to `publishing`, then the target directory is opened without symlinks and `RENAME_NOREPLACE` runs. On success the record becomes a `published` result (with information on whether durability was confirmed); on refusal it returns to `uploading`. The permission check and publication are serialized with permission changes.
4. `Abort` or expiry: unlink of the recognised staging name only, then removal of the record. The owner can cancel an upload even after losing Create. If the removal fails, the quota stays reserved and the broken upload cannot be published. A published upload cannot be cancelled.

Two uploads to the same name are decided by an atomic OS operation — at most one wins. There is no overwrite option. A missing parent directory gives an error; the application does not create a whole tree automatically (the interface creates folders level by level for folder uploads). Rename and deletion are described in "Rename and trash"; replacing existing content is possible only through the editor (previous version to the trash).

`Commit` returns `published` and `error` separately. `published=true, error!=nil` means the name was published, but e.g. the directory fsync did not confirm durability. This must never be interpreted as permission to delete the target or overwrite it again.

**Idempotency.** The publication result is kept for `ResultRetention` (24 h), also across restarts. A repeated commit of the same ID by the owner returns `published=true`, and if durability was not confirmed, retries the fsync of the target directory and the state. `Status` then returns `state: "published"` and `durability_confirmed`. The result is not revealed to other users (404) and does not require re-checking the target path — it performs no data operation except the directory fsync. The number of results is limited to `8 × MaxUploads`; the oldest are removed. After the result expires, a repeated commit returns 404, so the client should retry the commit shortly after losing the response, not a day later.

## Process crash and resources

The state directory must be a private, pre-created `0700` directory owned by the process, outside all spaces (it may be on another mount). An `flock` on the state prevents two processes from using the same state at the same time. The operator must not run several instances with different state directories for the same spaces — limits and `.filedeck` are local to an instance. `upload-*.part` files left in the state by versions from before spaces are removed at startup.

Upload and trash state lives in `uploads.db` (bbolt, schema v2; v1 records without a space are rejected at startup) in the state directory, opened relative to the state handle without symlinks; the file must be regular, `0600`, owned by the process, without hardlinks. The staging name follows from the record ID (`upload-<ID>.part`) and is not stored separately. `Close` and stopping the server keep uploads for resuming; the CLI `put` command cancels its own failed upload.

Recovery at startup:

| Record | Staging | Result |
|---|---|---|
| unreadable or inconsistent (ID ≠ key, missing/invalid space, invalid target path, size over the limit, offset out of range) | any | record removed, staging removed as an orphan |
| `uploading` / `publishing`, space missing or read-only | — | record removed |
| `uploading` / `publishing`, expired | present | removed together with the staging file |
| `uploading` / `publishing` | present, longer than the offset | truncated to the offset (unconfirmed bytes), resumable as `uploading` |
| `uploading` / `publishing` | present, shorter than the offset | confirmed bytes are gone — upload removed |
| `publishing` | missing | the rename happened: `published` result, a retried fsync decides `durability_confirmed` |
| `uploading` | missing | removed (e.g. a crash between the unlink and the record removal) |
| `published` | — | kept until the end of retention |

`rename` is atomic, and staging is removed only by the `Abort`/expiry path (impossible during `publishing`), so the presence of the staging file unambiguously resolves a crash during publication. If the `rename` was not persisted before a system crash, the staging file comes back and the upload is `uploading` again — a "published twice" state never arises. Staging files without a record are removed; a symlink or hardlink under a recognised name stops the startup (without removing anything). Cleanup is not recursive. The staging scan is limited to 10,000 names per space. The state and `.filedeck` directories belong to the application and are not a place for user files.

Upload expiry is absolute (`TTL` from `Begin`, default 1 h) and is not extended by activity; a restart does not renew it. After limits are lowered in the configuration, uploads exceeding the new `MaxFileBytes` are rejected at startup, while an excess in number or reservation only blocks new `Begin` calls. Uploads belong to the account ID; a disabled account can neither continue nor publish them, but they expire normally.

Cost: every chunk means two fsyncs (data and record), and `Begin` writes the record under the global service lock. There are no content checksums — integrity towards the client is provided by the offset and size, not a hash.

The limits are based on reserving the declared size; they are not a full filesystem quota. Data appended by other applications, existing user files and filesystem overhead do not fit into this reservation. The server calls `Expire` every minute and sets a 60 s read and write deadline for every request (a download's write deadline moves forward while data flows). `Context` alone does not interrupt an arbitrary blocked `io.Reader`, syscall or hung network mount. The API limits concurrent requests to 64 (no queue — the excess gets 503).

## Accounts, sessions and the HTTP API

**Store.** `identity.db` (bbolt, schema v1) lives in the private state directory and is opened relative to the directory handle with `O_NOFOLLOW`; the file must be regular, `0600`, owned by the process, without hardlinks. Upload recovery removes only `upload-*.part` names, so it never touches the database. The file is locked by a running server, which is why `bootstrap` and `reset-password` require stopping it.

**Accounts.** Name `^[a-z0-9][a-z0-9._-]{2,63}$`, password 12–1024 characters, Argon2id (t=3, 32 MiB, p=1). Operations that need hashing go through a gate of 2 concurrent computations; the excess gets 429 instead of a queue. A non-existent user is verified against a dummy hash. Max. 1000 accounts. The first administrator is created only in an empty database: with the `bootstrap` command or in setup mode (below). Account permissions are a map space → List/Read/Create/Modify (with `*` for all); an administrator gets no file access from the role itself, while the first administrator gets `*` = everything. Accounts stored before spaces were introduced (the `permissions` field) are converted to `*` when read; an administrator with the full set of that time (List|Read|Create) also gets Modify, regular accounts do not.

**Sessions.** A token of 32 random bytes; the database stores only its SHA-256. Every account has a version counter; a password change, reset, change of role, disable state or permissions increments the version and removes the account's sessions in the same transaction. A session is valid only with a matching version. It expires after 30 min of inactivity or 12 h. A new login beyond 8 sessions removes the oldest; logging in with an existing cookie replaces the previous session. Every authenticated request writes `LastSeen` (a transaction with fsync) — simplicity at the cost of performance under heavy traffic.

**Transport and origin.** Modes: HTTPS with Filedeck's own TLS, an explicit `ProxyCIDR` (connections from outside the CIDR rejected, forwarded headers ignored), or `InsecureLocal` for a loopback origin and peer only. `Host` must equal the origin. Requests other than GET/HEAD require an exact `Origin` and `X-CSRF-Token` = HMAC-SHA256(session token); `Sec-Fetch-Site: cross-site` is always rejected for the API. Cookie: `__Host-filedeck`, `Secure`, `HttpOnly`, `SameSite=Strict` (in local mode `filedeck-local` without `Secure`). Two cookies with the same name give 401. Responses: `no-store`, `nosniff`, CSP `default-src 'none'; sandbox`, no referrer; file content always as `application/octet-stream` + `attachment`, so the browser never renders user files in the application's origin.

**Input.** JSON only as `application/json`, max 16 KiB, no unknown fields and no data after the object. An upload chunk is at most `MaxChunkBytes`. Only single ranges. Errors are mapped to fixed codes without internal details.

**Administrative operations** require the role, CSRF and re-entering the password (`reauth_password`), and are subject to the login limit. An account change updates the `core.Service` policy immediately; a disabled account has an empty policy. **Deleting an account** (`DELETE /api/users/{id}`) removes the account, its name and all its sessions in one transaction, then clears its policy — which deletes its public links. An administrator cannot delete their own account (409 `delete_self`), and the last active administrator can be neither deleted nor disabled nor demoted (409 `last_admin`). Files the account uploaded and trash records naming it stay; the name can be reused by a new account with a new ID. Uploads in progress of a deleted account can no longer be published and expire normally.

**Order of revocation and publication.** Login, logout, password change and administrative operations take the exclusive `security` lock; an upload commit takes the shared lock and only then authenticates the session. The body of requests covered by the exclusive lock is read before taking it, so a slow client cannot block accounts. Guarantee: after a completed logout/disable, no commit from the old session will publish a file. No guarantee: listing, downloading and `PATCH` started before the revocation may finish (PATCH data only goes to private staging).

**Login limit.** Token bucket: 10 attempts per peer address (refilled at 10/min) and 20 globally (1/s), max. 4096 tracked addresses. Covers login, password change and reauth. Behind a proxy all attempts share the proxy's address — a deliberate trade-off against trusting `X-Forwarded-For`. The global limit protects the CPU but lets an attacker temporarily make logging in harder for others.

**Out of scope.** MFA, account lockout after failed attempts, a security audit log, listing and selectively revoking one's own sessions.

## Web interface

`internal/web` serves only embedded files (`/`, `/s/{token}` and `/assets/{name}` without subdirectories), through the same `Host`/TLS/proxy checks as the API. The page gets its own CSP: `default-src 'none'`, scripts, styles, images and connections only from the same origin, `form-action 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `require-trusted-types-for 'script'; trusted-types 'none'` — the browser rejects every assignment of an HTML string to `innerHTML` and similar sinks, so a file name cannot become code even with a bug in the JS. API responses keep the CSP with `sandbox`.

The client keeps the CSRF token only in memory and reads it from `/api/auth/me` after a reload; the session cookie stays `HttpOnly`. A download is a plain link to `/api/content` with `Content-Disposition: attachment` and `application/octet-stream`. An upload sends chunks according to the offset confirmed by the server, resynchronises through the status after errors, and retries the commit (idempotent). The upload ID is remembered in `localStorage` under a user+path+size+modification-date key so the same file can continue after a reload — a convenience, not a permission: the server checks the owner anyway. Blocking `Sec-Fetch-Site: cross-site` applies only to `/api/`, so a link from another site opens the interface but performs no operation (the `SameSite=Strict` cookie is not sent anyway).

Creating a folder (`POST /api/folders`) requires Create, creates exactly one directory in an existing parent opened without symlinks (`mkdirat`), never replaces an existing object and is serialized with session revocation, like a commit.

## Docker deployment

A `scratch` image with a single static binary, built for `linux/amd64` and `linux/arm64` (cross-compiled). Default layout: volumes `filedeck-data` (`/data`) and `filedeck-files` (`/files`) — in the image these are empty mount points with mode `1777` (sticky, like `/tmp`), copied into new named volumes. At startup the process creates in them (only the last path component, without overwriting existing entries) `/data/state` with mode `0700` and the `files` space in `/files/own` with `FILEDECK_DIR_MODE`, as the actual UID of the process — any `FILEDECK_USER` works without `chown`. An existing entry is then verified as usual (a symlink or a foreign owner of the state is rejected). The sticky bit ensures that another UID cannot remove or replace these directories; on the host the volumes live in Docker's directory, accessible only to root. There is also an empty `/spaces` for host directories. `HEALTHCHECK` calls `filedeck healthcheck`, which connects to `127.0.0.1` on the listening port (without certificate verification; the connection never leaves the container) and requests `/healthz`; that endpoint answers only loopback connections, before any other checks, and returns no data. Configuration through `FILEDECK_*` (flags take precedence). Transport modes in the container:

- **self-signed (default in compose)** — an ECDSA P-256 certificate for the host from `FILEDECK_ORIGIN`, valid for 397 days, stored in the state as `tls-self-signed.pem` (0600, atomic write, read without following symlinks). Regenerated when the host changes or 30 days before expiry. SHA-256 fingerprint in the log. It protects the transmission and allows `__Host-`/`Secure` cookies, but trust in the certificate depends on manually verifying the fingerprint.
- **reverse proxy** — `FILEDECK_PROXY_CIDR` + HTTP on the Docker network; see the transport section.
- **own certificate** — `FILEDECK_TLS_CERT`/`FILEDECK_TLS_KEY`.

`-insecure-local` does not work in a container with a published port: the peer is the Docker network gateway, not loopback — as intended. Compose publishes the port only on the host's `127.0.0.1` by default. A password reset is a one-off `docker compose run` with the service stopped (state lock).

**Setup mode.** If there is no active administrator when `serve` starts, the server starts and prints a one-time code in the log (80 random bits, 16 characters without ambiguous letters, groups of 4). The code lives only in memory and changes on every start. `POST /api/setup` with the code, name and password goes through the same transport, `Host` and `Origin` checks as the rest of the API, shares the attempt limit with login (10/min per address, 20/min globally — guessing the code is infeasible), compares the code in constant time and runs `Bootstrap`, which itself refuses if any account exists; after success the code is cleared. The code is not a password: whoever can read the container logs also has access to the Docker host. Passwords never go to logs or environment variables. Until setup, other endpoints work normally (without accounts they return 401).

## SMB/NFS and external changes

Serving a directory on a local disk that is exported over SMB/NFS in parallel is a different case from writing to an SMB/NFS mount on Filedeck's side (a space from a host that mounts the share itself). In the latter case `renameat2(RENAME_NOREPLACE)` is required: the CIFS client supports it, NFS does not — publication, rename and trash then return an error instead of risking an overwrite. The (device, inode) comparison protecting `.filedeck` on CIFS depends on stable inode numbers (the default `serverino`; with `noserverino` the client generates them) — not tested on a real share; the name-based protection works independently. The same applies to the object identity of public links. The mechanisms were tested on a local filesystem and on Docker bind mounts. No tests of SMB/NFS server failures, network disconnection, cache semantics or reconnect were performed. The `selftest` command checks the required properties on a real mounted directory.

Before declaring support for a specific configuration, tests of `renameat2`, fsync, locks, timeouts and behaviour after a failure are needed. We do not replace missing atomicity with an Exists+Rename or Copy+Delete sequence. If a source file is edited externally at the same time, reading/uploading is not a snapshot. Consistent snapshots and safe overwriting of existing files remain a separate project.
